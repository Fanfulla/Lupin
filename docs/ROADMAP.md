## Measured optimizations (research 2026-07-19)

1. ~~**Keep-alive on the connections towards the provider**~~: **done** 2026-07-19 with the user's approval (`server/dispatcher.ts`). Node's default dispatcher closed the connection after **4 seconds** of inactivity, so every user turn longer than that paid the handshake again: **1 TCP RTT plus 1 to 2 TLS RTTs**, that is 160 to 240 ms towards the US and 600 to 750 ms towards Asia. Now a global undici `Agent` with `keepAliveTimeout: 30_000`, installed by the daemon and by the doctor's ephemeral server. The `undici` dependency was added (pure JS, nothing native).
2. **Compression on SSE routes**: gzip and brotli buffer to fill the window and destroy streaming. Hono fixed this in `honojs/hono#3833` (January 2025) by excluding `text/event-stream`; we are on hono ^4.12 so the fix is there, and we do not apply compress. Never introduce it on SSE routes.
3. **No action on Nagle**: `noDelay: true` is already the default in Node 20+ (`nodejs/node#42163`).
4. **Outbound HTTP/2: to be avoided**: it is experimental opt-in in undici and has an open hang bug on the second request reused on the same connection, which is exactly a proxy's pattern.
5. **Prompt caching**: no mapping action to take (SPEC-TRANSLATION §5ter). Prefix stability is covered by `test/cache-stability.test.ts`; the `cache_control` check is implemented in the doctor (a preflight on passthrough profiles), and **running it live on DeepSeek and Z.AI is still pending**, since it needs an API key for those providers.

The main cause is the **sixth defect** found a few hours later (see below): the undici `Agent` cut every request at 300s instead of the declared 600s, and mapped it to a **retryable** 529. ### Measuring the prefill: the answer is a memory wall, not a throughput

Goal: find out whether a local model on this machine can hold the harness. The measurement never got as far as producing a tokens per second number, and the reason **is** the result.

Measured constraints, on an RTX 3080 with 10 GB, `gemma-4-12b-qat` Q4 (6.66 GiB of weights):

| Loaded window | Behaviour |
|---|---|
| 8,192 | answers a minimal prompt in around 6s; **but it is below the harness floor of 46,075 tokens**, so every Claude Code request fails |
| 65,536 | it fits the harness, but VRAM sits at **97% (9925/10240 MiB)**: a 200-token prompt does not come back for minutes |

**The two constraints cannot be satisfied together with this model on this card.** Raising the window to fit the harness blows up the KV cache and pushes the model out of fast memory. Today the doctor checks only the context floor (§3.1): the preflight would say "fine" at 65,536 and then the session would die of slowness.

The practical consequence for choosing a local model on 10 GB: the model needs its **weights plus the KV cache at around 64K** to fit under 10 GB. Among the installed ones, `qwen/qwen3.5-9b` (262,144 declared, around 5.5 GiB at Q4) is the candidate with the most headroom; `qwen3-8b` is excluded up front because its theoretical maximum (40,960) is already below the harness floor.

A methodological note from the same measurement: **killing the client does not cancel the work on the server**. Every abandoned attempt stayed queued on llama-server and skewed the next one; measurements must be taken after `lms unload --all`, not merely after closing the calling process.

## Risks and mitigations
1. **Claude Code changes protocol or env** (frequent releases): the weekly doctor in CI against the latest Claude Code is also the canary for regressions.
2. **Poor tool calling in third-party models**: expectations managed by the doctor (by design), adapters in M5.
3. **Model names that change** (for example the exact Kimi K3 id): never hardcode them in the sources, only in the default profiles in `docs/SPEC-PROVIDERS.md` plus the config, each with a verification date.
