# SPEC: translation core (Anthropic Messages API to OpenAI Chat Completions)

The specification of Lupin's technical heart. Every section is written to be implementable and testable in isolation. The primary direction is always: **Anthropic request to provider**, **provider response to Anthropic**. Claude Code only speaks Anthropic; the provider does not know it exists.

## 0. Endpoints to implement (ingress)

| Endpoint | Mandatory | Notes |
|---|---|---|
| `POST /v1/messages` | Yes | Streaming (SSE) and non-streaming. 99% of the traffic. |
| `POST /v1/messages/count_tokens` | Yes | Claude Code calls it to manage the context. See §7. |
| `GET /v1/models` | Recommended | Feeds the Claude Code model picker. Returns the models of the active profile. |
| `GET /health` | Internal | Used by `lupin doctor` and the CLI. |

Ingress auth: Claude Code sends `x-api-key` or `Authorization: Bearer` carrying the value of `ANTHROPIC_AUTH_TOKEN`. Lupin accepts one fixed local token (generated by `lupin init`) and discards it: the real auth towards the provider is added by the proxy.

| Anthropic | OpenAI Chat Completions | Notes |

| `system` (string or array of blocks) | a `{role:"system"}` message at the top | If it is an array: concatenate the `text` blocks with `\n\n`. Remove every `cache_control`. See §5. |

## 2. Mapping messages and content blocks

Anthropic uses only `user`/`assistant` with block content; OpenAI uses 4 roles. Conversion rules, in order:

1. **A user message with `tool_result` blocks only** becomes one or more OpenAI `{role:"tool", tool_call_id, content}` messages, one per block, in the same order.
2. **A mixed user message** (tool_result plus text) becomes the `role:tool` messages first, then a `role:user` message with the rest. The relative order must be preserved: OpenAI requires the `role:tool` messages to immediately follow the assistant message carrying the matching `tool_calls`.
3. **An assistant message with `tool_use` blocks** becomes an assistant message with `tool_calls[]`. See §3.
4. **`text` blocks** become a string (or a `{type:"text"}` part when the message also contains images).
5. **`image` blocks** `{source:{type:"base64", media_type, data}}` become `{type:"image_url", image_url:{url:"data:<media_type>;base64,<data>"}}`. Only in user messages; if a provider does not support images, the answer is an explicit Anthropic-format 400, not a silent drop.
6. **`thinking` and `redacted_thinking` blocks** inside history assistants are dropped (the provider did not generate them and does not understand them).
7. **`tool_result.content` as an array of blocks** (text plus images): the OpenAI `role:tool` message only accepts a string, so the text blocks are concatenated and the images in tool results are dropped with a warning (a rare case: MCP screenshots). Documented as a translate-mode limitation.
8. **`tool_result.is_error:true`** prefixes the content with `"Error: "` (a convention; OpenAI has no such field).

### Tool call IDs

Anthropic uses `toolu_*`, OpenAI uses `call_*`. The proxy does NOT rewrite the IDs: it passes them through in both directions. The constraint to respect: the `id` inside the assistant's `tool_calls` and the `tool_call_id` of the following `role:tool` message must match, and they match automatically because both derive from the same `tool_use.id` of Claude Code. Some providers validate the `call_` prefix: when a profile carries the `strictToolCallIds` quirk, the proxy rewrites `toolu_X` to `call_toolu_X` on the way out and strips it back on the way in (an in-memory mapping table for the session).

## 3. Tool mapping

Request:

```
Anthropic: {name, description, input_schema}          (input_schema = JSON Schema)
OpenAI:    {type:"function", function:{name, description, parameters}}
```

`input_schema` becomes `parameters` as is. Two cautions: (a) some providers reject schemas with `format`, `$ref` or `additionalProperties`, hence an optional sanitization behind a profile quirk; (b) tool names: Claude Code uses long names for MCP tools (`mcp__server__tool`) while OpenAI limits them to 64 chars and `[a-zA-Z0-9_-]`, so when a name exceeds that the proxy truncates and hashes it on the way out and keeps the inverse map for the response. This is MANDATORY: without it, MCP servers with long names break silently.

Response (non-streaming):

```
OpenAI:    message.tool_calls[i] = {id, function:{name, arguments:"<json string>"}}
Anthropic: content[] += {type:"tool_use", id, name, input:<json object>}
```

`arguments` is a JSON STRING: parse it; when the parse fails (the model produced malformed JSON), v1 returns an `api_error` with a clear message; M5 does automatic repair (see DESIGN §8).

## 4. Non-streaming response mapping

| OpenAI | Anthropic |
|---|---|
| `id` | `id` (prefix `msg_` when absent) |
| `choices[0].message.content` | a `{type:"text"}` block (when not empty) |
| `choices[0].message.tool_calls[]` | `{type:"tool_use"}` blocks after the text ones |
| `choices[0].message.reasoning_content` / `reasoning` (DeepSeek and similar) | a `{"type":"thinking","thinking":...}` block at the head of the content (2026-07-19: implemented, no longer dropped) |
| `choices[0].finish_reason` | `stop_reason`: `stop` to `end_turn`, `length` to `max_tokens`, `tool_calls` to `tool_use`, `content_filter` to `end_turn` plus a log warning |
| `usage.prompt_tokens` | `usage.input_tokens` (net of `cached_tokens`, see the row below) |
| `usage.completion_tokens` | `usage.output_tokens` |
| `usage.prompt_tokens_details.cached_tokens` | `usage.cache_read_input_tokens`, only when greater than 0. The semantics differ between the two protocols: OpenAI's `prompt_tokens` INCLUDES the tokens read from cache, Anthropic's `input_tokens` EXCLUDES them. So: `input_tokens = prompt_tokens - cached_tokens` (clamped at 0) and `cache_read_input_tokens = cached_tokens`. With 0 or absent the field is omitted: never invent a cache receipt the provider did not give (2026-07-24, backlog #11b; fixtures `cached-tokens` and `stream-cached-tokens`, real capture in `stream/tool-call`). The same holds for streaming (the usage accumulator of §5) and non-streaming, through the same mapper. |
| (none) | `type:"message"`, `role:"assistant"`, `model` (the original name Claude Code asked for, not the real one), `stop_sequence:null` |

Critical rule about `choices`: always use `choices[0]` only, and send `n=1`.

## 5. Streaming: the SSE state machine

Anthropic emits typed events; OpenAI emits flat delta chunks. For every request the proxy keeps state: the current `blockIndex`, the type of the open block, and a usage accumulator.

The sequence to produce (the order is mandatory):

```
event: message_start        -> on the first chunk received. usage.input_tokens estimated or 0, corrected later in message_delta.
event: content_block_start  -> when each block opens (index growing from 0)
event: content_block_delta  -> for every fragment
event: content_block_stop   -> when each block closes
event: message_delta        -> stop_reason plus usage.output_tokens
event: message_stop         -> always last
event: ping                 -> keep-alive every ~15s when the provider is slow
```

Translation algorithm for OpenAI chunks:

1. A non-empty `delta.content`: if no text block is open, close the current block if any, emit `content_block_start {type:"text"}`, then `content_block_delta {type:"text_delta", text}`.
2. `delta.tool_calls[j]` with a new `index`: close the current block, emit `content_block_start {type:"tool_use", id, name, input:{}}` (id and name arrive in the first fragment of the call); the following `function.arguments` fragments become `content_block_delta {type:"input_json_delta", partial_json}`.
3. `finish_reason` present: close the current block, emit `message_delta` with the mapped stop_reason (§4) and the usage (from the final chunk with `include_usage`), then `message_stop`. A `data: [DONE]` must NOT be emitted (that is OpenAI syntax, not Anthropic).
4. A malformed chunk, or the provider connection dropping mid-stream: emit an `event: error` in Anthropic format and close the stream. Never leave the stream hanging: Claude Code times out after around 10 minutes and the user has no idea why.

Known traps: (a) some providers send `delta.tool_calls` with no `index`, so assume 0; (b) some split name and id across chunks, so accumulate until `name` is complete before emitting `content_block_start`; (c) Ollama and LM Studio may send everything in a single chunk; (d) `arguments` fragments can split UTF-8 in half, so buffer bytes and emit whole runes.

Traps OBSERVED in real captures (OpenRouter/mistral-nemo, 2026-07-18, `test/helpers/captures/`): (e) SSE comment lines (`: OPENROUTER PROCESSING`) used as keep-alive, which must be ignored (standard SSE); (f) several SSE frames can arrive fused in a single transport chunk, and one frame can arrive split across two chunks, so buffer and split on `\n\n`; (g) `finish_reason` repeats across chunks, so handle it idempotently (the first one wins); (h) the usage (`include_usage`) arrives in a final chunk AFTER the first `finish_reason`, so `message_delta` and `message_stop` are emitted at `[DONE]` (or when the stream closes), not at the first `finish_reason`; that `message_delta.usage` also carries the corrected `input_tokens` (the `message_start` had started at 0).

## 5bis. Model dialects: normalizing the output

Beyond the protocol (the API fields) there is the model's **dialect**: how it really formats its output. Content that is syntactically valid for OpenAI can still be garbage for Claude Code. The normalization pipeline works on the content arriving from the provider, BEFORE the mapping of §4 and §5, and is enabled per profile through quirks:

| Dialect | Problem | Normalization (quirk) |
|---|---|---|
| Inline thinking (`<think>...</think>`, DeepSeek R1-distill, Qwen and others) | raw reasoning ends up in the text shown to the user and pollutes the Edits | `stripThinkTags`: remove the block (v1) or map it to a `thinking` block (v2). While streaming: a stateful filter that survives tags split across chunks |
| Harmony channels (GPT-OSS: `analysis`/`final`) | as above | `harmonyChannels`: keep `final` only |
| Textual tool calls (`<tool_call>{json}</tool_call>`, Hermes-style XML, bare JSON, common on local models with imperfect templates) | the model "calls" the tool but no structured `tool_calls` arrives, so the agentic loop dies | `parseTextToolCalls`: recognize the known formats in the content and convert them into synthetic `tool_use` blocks (with a generated `toolu_lupin_*` id). While streaming: buffer from the opening marker |
| Leaked special tokens (`<\|im_end\|>`, `<\|eot_id\|>` and friends) | dirty text at the tail of the answers | `stripSpecialTokens`: a fixed list of known patterns |
| "Loose" JSON in the arguments (single quotes, trailing commas) | the parse fails and the tool_use is lost | `looseJsonArguments`: a tolerant parser (for example jsonrepair) ONLY when the strict parse fails, with a log warning |

Rules: (1) every normalization is a per-profile quirk, NEVER on by default for serious cloud providers, since it would mask regressions; (2) every recognized dialect gets a fixture with real output from a model that exhibits it; (3) the doctor (SPEC-CLI §3) reports in its details when a normalization fired: that is valuable diagnostic information ("it works, but only thanks to parseTextToolCalls").

Boundary note: normalization repairs the *syntax* of the dialect. Repairing the *semantics* (a model that gets the Edit exact match wrong) is the territory of the behavioural adapters (M5, DESIGN §8). A sharp line between the two keeps complexity from arriving early.

### 5bis.1 Implementation (2026-07-19, `core/dialect.ts`)

**One engine for both paths.** `DialectNormalizer` is a state machine with `push(chunk)` and `flush()`: the non-streaming mapper calls it once on the whole content, the SSE translator calls it once per delta. Duplication is forbidden by construction, because the most frequent bug class in competitors is a normalization that behaves differently while streaming (CCR #1397: the reasoning transformer corrupts tool-call argument deltas; #1356: interleaved text and tool_call break the content blocks). The `streaming equals non-streaming` test feeds the same input character by character and as one block and demands identical segments.

**Hold-back.** Text whose tail could still become a marker is never emitted: a `<tool_call>` split across two chunks (`<to` plus `ol_call>`) is recognized as a whole one. The delay is bounded by the longest marker, never by the whole message: time-to-first-token stays intact.

**Markers as data.** The `RULES` table is the only place where dialect literals live: adding a model family means adding a row, never an `if` (CLAUDE.md rule 4).

### 5bis.2 Verified dialects (2026-07-19, research with adversarial refutation)

Every row was verified against the official Jinja chat template on HuggingFace and/or against the server-side parser code (vLLM, llama.cpp, SGLang, Ollama), then handed to a second agent tasked with **refuting** it. Unconfirmed markers were discarded, not implemented.

| Family | Opening to closing | Payload | Verified notes |
|---|---|---|---|
| Qwen3 (and most local models) | `<tool_call>` to `</tool_call>` | JSON `{"name":...,"arguments":{...}}` | tokens 151657/151658 are declared **`special:false`**: `skip_special_tokens` does NOT remove them, so they really do arrive in the content |
| GLM 4.5 to 5.2 | `<tool_call>` to `</tool_call>` | a **bare name** plus `<arg_key>`/`<arg_value>` pairs | the same marker as Qwen with a completely different payload: no JSON envelope. 4.5/4.6 put a `\n` after the name, 4.7+ do not |
| Qwen3-Coder | `<function=NAME>` to `</function>` | `<parameter=NAME>` blocks with **raw text values** | exactly one leading and one trailing `\n` are structural; the types are recovered from the schema |
| DeepSeek V3/R1 | `<｜tool▁calls▁begin｜>` to `<｜tool▁calls▁end｜>` | `function<｜tool▁sep｜>NAME` plus JSON in a fence | **fullwidth U+FF5C** bars, **U+2581** separators: the ASCII pipe here is a mistake that breaks the match |
| Kimi K2 | `<\|tool_calls_section_begin\|>` to `<\|tool_calls_section_end\|>` | `<\|tool_call_begin\|>functions.NAME:idx<\|tool_call_argument_begin\|>{...}` | **ASCII** pipes, not fullwidth: verified programmatically across all Kimi code paths |
| Mistral / Devstral | `[TOOL_CALLS]` to `</s>` or end of message | v13: `NAME[ARGS]{...}`; pre-v11: a JSON array | **no closing marker** in the grammar: recovery goes through `flush()` |
| Llama 3.x | `<\|python_tag\|>` to `<\|eom_id\|>` | JSON with `parameters` | active with `Environment: ipython` |
| GPT-OSS Harmony | `<\|channel\|>analysis<\|message\|>` to `<\|end\|>` | text | the `final` channel closes with `<\|return\|>`, not `<\|end\|>` |
| Kimi VL | `◁think▷` to `◁/think▷` | text | a separate branch with the U+25C1/U+25B7 triangular brackets |

Leaked tokens implemented: `<|im_end|>`, `<|im_start|>`, `<|eot_id|>`, `<|eom_id|>`, `<|end_of_text|>`, `<|endoftext|>` and the whole FIM family (`<|fim_prefix|>`, `<|fim_middle|>`, `<|fim_suffix|>`, `<|fim_pad|>`, `<|repo_name|>`, `<|file_sep|>`). The FIM ones are declared `special:false` in the Qwen vocabulary, which is exactly why they end up in the text.

**A trap confirmed by the research**: the confusion between the ASCII pipe (U+007C) and the fullwidth one (U+FF5C) is real and asymmetric. DeepSeek uses the fullwidth form, Kimi the ASCII one. A marker with the wrong character does not fail loudly: it simply never matches, and the tool call stays text. For the same reason these literals must not be "normalized" by any formatting tool.

**The implicit `<think>` case, now documented at the source**: on Qwen3 `*-Thinking` checkpoints the generation prompt ends with `<|im_start|>assistant\n<think>\n`, so the opening tag lives in the PROMPT and the model only emits `</think>`. That confirms the limitation declared above: without `reasoning_content` there is no way to reclassify that text without unlimited lookahead.

**Correct `stop_reason`.** When a tool call is recovered from text the provider closed with `finish_reason: "stop"`: Claude Code runs tools ONLY on `stop_reason: "tool_use"`, so the mapper rewrites it. Without this the recovery would be useless and the agentic loop would stay dead anyway.

**Declared limitation: an orphan closing tag.** Some templates pre-fill `<think>` in the prompt, so the model emits only `</think>`. Classifying the text before it as reasoning would need unlimited lookahead, that is buffering the whole message: the one cost a proxy cannot pay. The marker is removed and the text is left alone. Real recovery for those models goes through `reasoning_content` (§4), which those providers almost always expose.

**`thinking` blocks with no `signature`.** Verified live on 2026-07-19: Ollama 0.21.0, on its native Anthropic endpoint designed for Claude Code, emits `{"type":"thinking","thinking":...}` with no `signature` field. Lupin does the same. On ingress the thinking blocks in the history are dropped (§2 rule 6), so the round trip is closed.

**`looseJsonArguments`.** A tolerant parser written in house (no dependency): markdown fences, single quotes, trailing commas, truncated objects. It runs ONLY after the strict parse fails, both on native tool call arguments and on textual payloads.

## 5ter. Prompt caching: where it really acts (2026-07-19)

Cost is the number one motivation for users, and caching is the biggest lever. Research verified against the official documentation:

| Provider | Mechanism | Field to send | Discount |
|---|---|---|---|
| DeepSeek | automatic (context caching on disk) | none | around 98% (hit $0.0028/M vs miss $0.14/M), exposed in `usage.prompt_cache_hit_tokens` |
| Gemini | implicit and automatic on 2.5+ | none | 90% |
| Z.AI / GLM | implicit and automatic (4.5 to 5.x) | none | 50%, exposed in `usage.prompt_tokens_details.cached_tokens` |
| OpenAI | automatic from 1024 tokens | none | 50% on reads |
| Moonshot / Kimi | automatic on the standard endpoint | none | not quantified in the current documentation |

**Consequence for translate**: dropping `cache_control` (§2) is not a compromise but the correct choice. No OpenAI-compat provider has a per-block equivalent, and they all cache on their own without being asked. There is no 1:1 mapping to do.

### 5ter.1 `cache_control` in passthrough: who accepts it (verified 2026-07-19)

In passthrough the field is **not** dropped: it reaches the provider exactly as Claude Code sends it, on practically every request. A provider that **rejected** it would break every session on the first turn. The evidence gathered, keeping what is documented separate from what is inferred:

| Provider | Outcome | Strength of evidence | Source |
|---|---|---|---|
| **LM Studio** (local) | **accepted** | **our own live probe** (HTTP 200) | `lupin doctor lmstudio`, 2026-07-19 |
| **Moonshot / Kimi Code** | **accepted** | **our own live probe** (HTTP 200, 3 valid runs out of 3) | `lupin doctor kimi-sub --json`, 2026-07-19 |
| **DeepSeek** | accepted and **ignored** | **explicitly documented** | api-docs.deepseek.com/guides/anthropic_api/ marks `cache_control` as `Ignored` on `text`, `tool_use` and `tool_result` blocks and on `tools[]` |
| **Z.AI / GLM** | accepted (not rejected) | **inferred, not documented** | docs.z.ai never names the field; the official Claude Code guide points at `api.z.ai/api/anthropic` with no caveat. If the field returned 400, the integration they sell would break on the first request of every subscriber |

**A note on the strength of evidence**: only DeepSeek has an official statement one can cite. Kimi does not document it at all (there is an open issue, `MoonshotAI/Kimi-K2#129`, asking exactly this, with no answer), but our probe covers it better than any documentation. Z.AI stays the only row with no direct proof: a live probe there needs a key.

**Practical consequence**: no provider rejects the field, so byte-faithful passthrough (ADR-7) is safe. Nobody *uses* it either: they all cache automatically on the prefix. The field is therefore harmless and useless, which leads to the point below.

**The risk moves**: since caching is a byte-per-byte prefix match, what matters is no longer a field to map but the **stability of the serialization**. If the translated prefix (system plus tools) changes by even one byte between two requests of the same session, the cache misses silently and the user pays full price with no error to look at. The mapper builds keys in a fixed order and never iterates unordered structures; `test/cache-stability.test.ts` locks the property down: the same request produces an identical body, and the prefix stays unchanged when only the last turn changes.

**It holds in passthrough too, and matters more there**: on local runtimes the roughly 46K-token prefill dominates every turn on modest hardware, and llama.cpp and LM Studio skip it only while the prefix stays byte-identical. `test/passthrough.test.ts` locks the same property down on the passthrough branch (see SPEC-PROVIDERS §3ter).

**Consequence for passthrough**: `cache_control` passes through intact, with no stripping (ADR-14: a byte-per-byte pipe). Empirical proof already on record: the real Claude Code session on Kimi K3 of 2026-07-18 (5 requests, all 200). Claude Code injects `cache_control` on its own on every request, so those 200s prove the endpoint accepts it. For DeepSeek and Z.AI the equivalent evidence is missing: a dedicated doctor check ("a request with `cache_control` returns 200" on every passthrough profile) would close the doubt with direct proof instead of inference.

## 6. Error mapping

Anthropic format, always, including for errors generated by the proxy:

```json
{"type":"error", "error":{"type":"<type>", "message":"<msg>"}}
```

**Credential scrubbing (2026-07-19, ROADMAP backlog #4)**: every outgoing error message goes through high-precision patterns that redact `Bearer <token>`, JWTs (`eyJ...`), `sk-...`/`AIza...` keys, `?key=` parameters and email addresses with `[redacted]`. Legitimate messages are never mangled. A single implementation in `core/errors.ts` (the `errorBody` choke point), covered by test fixtures.

| Condition | HTTP | `error.type` |
|---|---|---|
| Provider 401/403 | 401 | `authentication_error` |
| Provider 429 | 429 | `rate_limit_error` plus the `retry-after` header when present |
| Provider 400 (schema, context length) | 400 | `invalid_request_error` with the provider message included |
| Provider 5xx / timeout / network | 529 | `overloaded_error` (Claude Code retries automatically on 529) |
| Proxy bug | 500 | `api_error` with a `[lupin]` prefix so it is distinguishable |

The provider's error message must ALWAYS be propagated inside `message` (truncated at 2000 chars): the user's debugging depends on it.

## 7. count_tokens

`POST /v1/messages/count_tokens` receives the same body as messages and answers `{"input_tokens": N}`. Strategy: (a) a provider with an equivalent endpoint gets used; (b) otherwise a local estimate with an approximate tokenizer (`o200k_base` through tiktoken-js is fine for all modern models; a ±10% error is acceptable, since Claude Code uses it for context management, not for billing). Include in the count: the system prompt, the serialized messages, and the tools (JSON schemas are heavy). Images: base64 carries no dimensions, so a flat cost of 1500 tokens per image is used (a stable overestimate, better than ignoring them). In passthrough (§8): forward it; if the provider answers 404/405, fall back to the local estimate.

## 8. Passthrough mode

For Anthropic-native providers there is no translation: the proxy rewrites (a) the base URL, (b) the auth header (`x-api-key`/`Authorization` with the provider key), (c) `model` according to the slot mapping, and (d) forwards the body byte per byte, streaming included (a direct pipe, zero parsing, zero risk). Errors are normalized (§6) and logged in passthrough too. `count_tokens`: forward it when the provider supports it, otherwise use the local estimate (Moonshot and DeepSeek are not guaranteed to expose it).

## 9. Cross-cutting requirements

1. **Logging**: every request produces one structured line (timestamp, profile, requested model to real model, mode, latency, tokens, outcome). `lupin logs -f` tails it. Full bodies only with `LUPIN_DEBUG=1` (they contain the user's code: never by default).
   - **`streamError` (verified live 2026-07-19)**: an SSE stream can carry an `event: error` while the HTTP status stays 200. LM Studio answered that way to an over-context request. In passthrough the body is forwarded byte per byte (ADR-7) and must not be touched, but the log line said `status: 200` for a request that had failed entirely, so `lupin logs` showed a success. The fix is a tap that **observes without modifying** (every chunk is forwarded before being inspected) and emits a SECOND line with the `streamError` field, exactly as `dialect` already does: the stream closes long after the request line was written, and the HTTP status really was 200. The decoder stays in streaming mode, so a marker split across two chunks is still recognized.
   - **`usage` (implemented 2026-07-20)**: token counts were required by this section from the first draft but had never been implemented. The gap is not cosmetic: **the proxy is the only place that sees 100% of the traffic**. Claude Code subagents talk to the proxy but write nothing into the main transcript, so a transcript-based audit misses them entirely. Measured on 2026-07-20 on a real Kimi session: 332 requests to Lupin against 113 turns visible in the transcript, and the extra ones all concentrated in the window where the research subagents were running. Same mechanism as `streamError`: a tap that forwards every chunk before inspecting it, and a second line with the `usage` field. In SSE the input count arrives in `message_start` and the final output count in `message_delta`, so both must be read; non-streaming reads `usage` from the body. Counts only, never content: that is the boundary that makes this compatible with point 2. The field is absent when the provider reports nothing: no invented zeros.
   - **`retryAfterMs` (implemented 2026-07-24)**: the milliseconds actually waited on the provider's `Retry-After` hint before retrying the same profile (SPEC-PROVIDERS §4ter). A wait that does not appear in the log is indistinguishable from a slow provider, and the line's latency includes it: without the field, a turn that took two seconds longer would have no explanation.
2. **Zero content persistence**: the proxy never writes prompts or responses to disk (except with explicit debug).
3. **Timeouts**: 600s towards the provider (agentic tasks are long); keep-alive pings towards Claude Code in the meantime.
4. **Port**: 3456 by default, configurable. Bound to 127.0.0.1 only.

## 10. Acceptance tests for the translation core

Every feature is covered by round-trip fixtures (Anthropic request to expected provider request; provider response to expected Anthropic response). Mandatory minimum cases:

1. Plain text, non-streaming and streaming.
2. A single tool call with a real MCP schema (the long name `mcp__server__tool`), full round trip with the tool_result.
3. Multiple tool calls in the same turn.
4. A tool_result with is_error and with a content array.
5. A base64 image in a user message.
6. A system array with `cache_control` to strip.
7. Streaming with a tool call split across 3 or more chunks, split UTF-8 included.
8. A 429 and a 500 from the provider during streaming.
9. max_tokens reached (`finish_reason:"length"`).
10. A long history with alternating tool_use/tool_result turns (simulating a real agentic session, 10 turns or more).

The definitive end-to-end test is `lupin doctor` (see SPEC-CLI §3): a headless Claude Code session (`claude -p`) that reads, edits and verifies a file using a test MCP server.
