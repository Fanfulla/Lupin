# AUDIT 2026-07-22: what is built and the objective gaps towards the best routing on Claude Code

> **Provenance.** A multi-agent audit on 2026-07-22 (workflow `lupin-routing-analysis`, run `wf_d2ae1173-8dc`, 25 agents):
> 5 area readers over the code plus 1 over the docs plus 1 web search on the competitors, consolidated into 16 candidate
> gaps, then **an adversarial verification of every gap against the code and the ADRs** (16 out of 16), then a
> completeness critic over the final list. The agents' evidence is reported **verbatim** (their working language);
> the summary sections were originally written in Italian and are translated here. Repo state at audit time:
> HEAD `aa55f58`, 279 tests of which 4 red (CRLF corruption of the captures, see §8).

## 1. Executive summary

**Tally of the 16 verified gaps: 4 MISSING, 12 PARTIAL, 0 already done, 0 rejected by an ADR.**

The structural fact: **translation is the mature part** of the project (a complete mapping, a single dialect engine over 8
families, a chunk-safe SSE machine, 12 centralized quirks, credential scrubbing). The real holes are elsewhere:

1. **Reliability bugs in already-shipped routing** (a cooldown that never fires with delegated slots and is wiped on
   every hot reload; mid-stream failures invisible to the health tracker; a watchdog that is never respawned). Effort S, maximum return.
2. **The two integration points Claude Code offers for free and we do not use**: gateway model discovery for the
   `/model` picker (the server side is ready, never wired into `lupin run`) and route configurability from the CLI.
3. **The declared moat (ADR-2) exists only on this machine**: the doctor CI has never run, `--submit` and the scoreboard
   have no code, and verified coverage sits at a third of the M4 criterion.
4. **Violations of the promise "the tool never lies about itself"** (pain point #1 in COMPETITIVE.md §D):
   local init announces a long-context threshold for a route that does not exist; the doctor's `--json` leaks `score: 0`
   in `notRun` runs against ADR-23; SPEC-PROVIDERS:116 claims a mid-session switch that was never verified; and
   nonexistent quirks are accepted in the config as silent no-ops.
5. **A publication blocker found by the critic**: the daemon and the watchdog hardcode `tsx` and `.ts` paths, so a Lupin
   installed from npm cannot start its own daemon.

The competitive comparison (§6) shows that CCR has already won the routing *feature* race (36k stars, a sandboxed router
script, subagent tags, retry with Retry-After). The objective path towards "the best routing on Claude Code" stays the
ADR-2 one: **correct, honest routing plus knowing where to route better than anyone** (the doctor and the scoreboard),
not chasing CCR on features.

## 3. Gap dossier (consolidated by impact, with the full evidence)

### 3.1 `subagent-routing` — No subagent/background-agent routing: all spawned-agent traffic routes only by slot

- **Bucket**: Routing core
- **Why it matters**: Subagent routing is CCR's #1 complaint theme (13% of issues) and CCR v3 ships a working CCR-SUBAGENT-MODEL tag mechanism, while Lupin deferred it to M5 (ADR-25 deferral, not rejection) so a user cannot send Task/Explore subagents to a cheap model while the main thread stays on a strong one beyond the single --bg haiku delegation.
- **Source of the claim**: docs-promises gap (ADR-25 deferred, COMPETITIVE §A 13%); competitor: claude-code-router v3 subagent auto-routing
- **Adversarial verdict**: **PARTIAL** (effort M)
- **Verifier evidence** (verbatim):

  > src/providers/resolve.ts:3,17-23,61-77 — routing dimensions are only slot-by-model-name (opus/haiku/sonnet) + content routes (longContext/vision/thinking); no subagent detection (no tag/system-prompt/header sniffing; grep 'subagent' in src/ hits only comments). Partial: src/cli/use.ts:44 `--bg` delegates the haiku slot to a cheap profile, and SPEC-PROVIDERS.md:67 designs the haiku slot as the subagent/background lane — so haiku-labeled subagent traffic IS routable to a cheap model today; sonnet-labeled Task/Explore subagents are indistinguishable from the main thread. Not rejected: docs/DECISIONS.md ADR-25 (line 31) says "complexity routing e subagent routing (rimandati a M5)" — explicit deferral to M5, and docs/ROADMAP.md:188 'No deliberati' does not list it.

### 3.2 `cooldown-blind-spots` — Cooldown state is recorded but not consistently acted on (delegation name mismatch, failover cooldown ignored, hot-reload wipe)

- **Bucket**: Reliability
- **Why it matters**: Failures are recorded under the resolved (post-delegation) profile name while the skip only checks activeProfile (ingress.ts:198,265 vs :343), the failover's own cooldown is never consulted before dispatching to it (ingress.ts:346,359), and every config-file touch rebuilds the tracker from scratch (start.ts:20) — so the §4sexies cooldown feature silently never fires for exactly the economy/delegation setups init creates.
- **Source of the claim**: src/server audit gaps (ingress.ts, health.ts, start.ts); SPEC-PROVIDERS §4sexies promise
- **Adversarial verdict**: **PARTIAL** (effort S)
- **Verifier evidence** (verbatim):

  > Feature exists and works flat-case: src/server/health.ts (tracker per §4sexies), ingress.ts:340-349 (skip), test/health-cooldown.test.ts:117-137 (e2e, flat slots only), ADR-25 docs/DECISIONS.md:31. Blind spot 1 CONFIRMED: failures recorded under post-delegation name (ingress.ts:198 via resolve.ts:130-132; recordFailure at ingress.ts:265,294,319) while skip checks only config.activeProfile (ingress.ts:343) — with slot delegation the skip never fires, diverging from SPEC-PROVIDERS §4ter "whichever delegated profile failed" which §4sexies extends. Blind spot 2 CONFIRMED: start.ts:15-20 rebuilds createApp(next) without opts.health on every config touch → fresh tracker (ingress.ts:41); daemon runs start.ts (daemon.ts:55-58); ADR-25 only sanctions reset on restart, not 500ms-poll hot reload. Blind spot 3 WEAK: failover cooldown unchecked at ingress.ts:346,359 is factual but §4ter forbids cascades so no alternative exists — by-design, not a defect. Framing correction: init economy presets are NOT affected (defaults.ts:60-64 use same-profile string route targets; resolve.ts:100-105 keeps startName); delegation comes from `lupin use --bg` (use.ts:44) and hand-written configs. Not rejected: the ADR-25 rejected column covers persistence/auto-activation/4-state machine only; ROADMAP.md:188 "No deliberati" unrelated.

### 3.3 `midstream-failures-invisible-to-health` — Mid-stream provider failures never reach the health tracker

- **Bucket**: Reliability
- **Why it matters**: recordSuccess fires at response-header time and the streamError tap never calls recordFailure (ingress.ts:270,326,146), so a provider that reliably returns 200-then-dies mid-stream (the observed LM Studio failure mode) stays 'healthy' forever and is never cooled down or skipped to failover.
- **Source of the claim**: src/server audit gap; real capture lmstudio SSE-error-under-200 (ADR-7 context)
- **Adversarial verdict**: **MISSING** (effort S)
- **Verifier evidence** (verbatim):

  > src/server/ingress.ts:270 and :326 call health.recordSuccess at response-header time, before any body byte streams; the SSE tap at ingress.ts:146 is `(streamError) => logExtra({ streamError })` — log only, and grep confirms recordFailure is called only at ingress.ts:265/294/319, all pre-stream. Worse: recordSuccess deletes the failure state (src/server/health.ts:49-51), so a 200-then-event:error provider resets its own counter every request and can never reach the 3-failure cooldown threshold checked at ingress.ts:343. Not rejected: ADR-24 (docs/DECISIONS.md) scopes the 200+event:error response to logging only; ADR-25 rejects only persistence/auto-activation/4-state machine; ROADMAP.md:188 'No deliberati' does not mention it.

### 3.8 `retry-policy-single-hop` — No same-model retry with backoff/Retry-After — only one immediate failover hop

- **Bucket**: Reliability
- **Why it matters**: A transient 429 with Retry-After: 2 immediately burns the single failover attempt or surfaces the error, whereas CCR retries the same model honoring Retry-After with 1-30s exponential backoff and Bifrost gives every chain member its own retry budget — the most common flake class (momentary rate limit) is handled worse than in every major competitor.
- **Source of the claim**: src/server audit (ingress.ts:174-178, 351-361, single retry by SPEC §4ter); competitors: CCR retry mode, Bifrost network_config, LiteLLM num_retries
- **Adversarial verdict**: **PARTIAL** (effort M)
- **Verifier evidence** (verbatim):

  > Factually confirmed in-proxy: no same-model retry, no backoff, no Retry-After wait. src/server/ingress.ts:351-361 — one attempt() on the primary, then immediately one attempt on the declared failover profile, no delay ("un solo retry... niente cascate" per SPEC-PROVIDERS.md:130, §4ter); ingress.ts:178 defines retryable as 429/529 only. Retry-After is parsed (ingress.ts:316, src/server/translate.ts:58, src/core/errors.ts:85-94) but only re-emitted to the client (ingress.ts:507), never slept on. No ADR rejects same-model retry: ADR-6 (DECISIONS.md:12) covers only the doctor; ADR-25 (DECISIONS.md:31) rejects the Bifrost 4-state circuit breaker as "fuori scope single-user", not per-attempt retry; ROADMAP.md:188 "No deliberati" lists only semantic cache/TLS/GUI/context compression. BUT the verdict is partially_done, not missing, because the flake class is deliberately handled one loop up: SPEC-TRANSLATION.md:215-217 maps provider 5xx/timeout/network to 529 explicitly because "Claude Code fa retry automatico su 529", and Lupin forwards retry-after downstream so the client backs off correctly — so a transient 429/529 does get same-model retries (by Claude Code, through the proxy), plus §4sexies cooldown (SPEC-PROVIDERS.md:136-146, src/server/health.ts) stops re-probing a dead primary. The competitor comparison ("handled worse than every major competitor") overstates: CCR/Bifrost sit in front of arbitrary clients; Lupin's only client retries 429/529 natively. Remaining true gap: each client-level retry burns the failover hop immediately, and a Retry-After:2s hint is never honored proxy-side before failing over.

### 3.12 `local-window-knowledge-poisoned` — Local init stores 'max' context windows that can overstate the served window 32x, ready to mis-drive the dynamic threshold

- **Bucket**: Knowledge/verification
- **Why it matters**: init.ts:211-213 persists m.contextWindow regardless of contextWindowSource even though local.ts documents the 262144-advertised vs 8192-loaded case, so the moment a longContext route is added to a local profile the 0.8x threshold fires at ~26x the real window — the exact 'made-up window routes worse than an absent one' failure the spec excludes providers for.
- **Source of the claim**: src/config + src/providers audit gap (init.ts:211-218, local.ts:20-22); SPEC-PROVIDERS §4quinquies principle
- **Adversarial verdict**: **PARTIAL** (effort S)
- **Verifier evidence** (verbatim):

  > The loaded-vs-max distinction IS implemented up to the display layer but is dropped at persistence. Confirmed: src/cli/init.ts:211-218 (correct path — not src/config/) persists m.contextWindow into profile.contextWindows with no contextWindowSource check; src/providers/resolve.ts:68-72,94-95 derives the 0.8x longContext threshold from that map; and a second, live consumer the candidate missed — the doctor preflight src/doctor/run.ts:212-223 — would pass a max=262144 window against DOCTOR_MIN_CONTEXT=50000 while the served window is 8192, resurfacing the exact ADR-23 incident (docs/DECISIONS.md ADR-23). Partially done because src/providers/local.ts:23,124,128,148 already tracks contextWindowSource, prefers loaded_context_length, and init.ts:178 prints the 'max' suffix — which is everything SPEC-PROVIDERS §3ter point 5 rules (a)-(c) (docs/SPEC-PROVIDERS.md:106) actually mandate; the spec names this exact failure ("a threshold around 209k on a model that overflows at 8k: the route would never fire") but omits a persistence rule, so code matches spec letter while violating §4quinquies' principle (SPEC-PROVIDERS.md:179). Not rejected: no ADR covers window provenance (ADR-25 is about never auto-activating routes, orthogonal) and ROADMAP.md:188 'No deliberati' does not mention it. ### 3.14 `watchdog-respawn-gap` — Watchdog is only spawned on fresh daemon start, so long-lived sessions lose crash protection

- **Bucket**: Reliability
- **Why it matters**: spawnWatchdog runs only when ensureDaemon just started the daemon (daemon.ts:66-72); once a watchdog exhausts its 5-minute hold window and exits, later lupin run invocations never verify or respawn it, so a mid-session daemon death again surfaces as raw connection-refused — precisely the failure SPEC-CLI §6.4 exists to prevent.
- **Source of the claim**: src/server audit gap (daemon.ts:87-103, watchdog.ts:104-107); also untested per test-audit (watchdog.ts never imported by tests)
- **Adversarial verdict**: **MISSING** (effort S)
- **Verifier evidence** (verbatim):

  > daemon.ts:69 is the sole spawnWatchdog call site (grep-verified), gated inside the 'started' branch; the 'already-running' path (daemon.ts:49) returns with no watchdog check, and the watchdog pid is never persisted (daemon.ts:102), so no later invocation can verify it. The unsound assumption is explicit in the comment at daemon.ts:87-89 ("a live daemon means an older watchdog is redundant"). Not rejected: docs/DECISIONS.md ADR 1-25 never mention the watchdog; docs/ROADMAP.md:188 'No deliberati' lists unrelated items. Untested claim also confirmed: test/daemon-watchdog.test.ts re-implements the fallback inline (lines 52-59) and duplicates DAEMON_DOWN_MESSAGE (15-16), never importing watchdog.ts. One caveat: the gap's 5-minute-give-up scenario largely self-heals (watchdog exits only when the daemon is also dead, watchdog.ts:104-111, so the next run takes the 'started' path and respawns both); the genuine unprotected cases are a watchdog that dies while the daemon lives, and a daemon started with LUPIN_NO_WATCHDOG=1 (daemon.ts:92) which no later normal run ever protects. Spec anchor: docs/SPEC-CLI.md:82 (§6 criterion 4). Adjacent unclaimed bug noticed: during the 5-min hold the watchdog owns the port, so a lupin run in that window spawns a daemon that cannot bind while the watchdog only releases on health-OK or deadline (watchdog.ts:53-57, 77-88).

## 4. Blind spots from the completeness critic

### 4.1 Final pass (over the complete list of 16 verdicts)

Five dimensions the gap list does not cover, each supported by verified evidence:

1. Streaming protocol correctness under early/late failure: `finish()` in src/core/stream.ts:108-113 has no `started` guard (flag only set at :158-159), so a provider stream that dies before emitting any chunk produces `message_delta`+`message_stop` with no preceding `message_start` — a protocol-invalid SSE sequence Claude Code must parse — and the adjacent untested edge in src/server/translate.ts:116-131 (client cancel can enqueue the abort event into an already-closed controller) belongs to the same uncovered "translation correctness when the stream itself misbehaves" dimension.

2. Installability/packaging: daemon and watchdog spawn hardcode the tsx loader and `.ts` source entrypoints (src/server/daemon.ts:55-58 `spawn(process.execPath, ['--import','tsx', startTs])` resolving `./start.ts` relative to the repo, same pattern at :93-96), so any compiled/dist or npm-installed Lupin cannot start the daemon or watchdog at all — no gap addresses distribution beyond the dev checkout.

3. Error-typing loss that defeats the client retry loop the gap list relies on: under `clientErrorsWrappedIn500` any nested 4xx is flattened to a fixed `400/invalid_request_error` (src/core/errors.ts:98-100), so a wrapped 429 or 401 loses its `rate_limit_error`/`authentication_error` type and Retry-After — silently disabling exactly the client-side same-model retry that the retry-policy-single-hop verdict credits as mitigation (errors.ts:59-61, 92-95).

4. Doctor scoring construct validity (a blind spot distinct from the two doctor gaps): check 3 grants edit credit only if greet.js contains the literal `'"Ciao, "'` (src/doctor/plan.ts:205, so a functionally correct template-literal rewrite that prints "Ciao, world" loses the points), check 6 never verifies step B or ordering (plan.ts:236-240), and TRANSPORT_TERMINAL_REASONS covers only api_error/auth_error (plan.ts:147) — meaning the score the entire scoreboard positioning rests on partially measures string matching, not behavior.

5. Silent quirk/config degradation: profile `quirks` is validated only as `string[]` (src/config/config.ts:35 — grep confirms no KNOWN_QUIRKS runtime reader in config.ts), so misspelled quirk names and the two registry-declared-but-unimplemented quirks (strictToolCallIds, singleSystemMessage, per src/core inventory) are accepted as silent no-ops, and the spec-promised loss warnings (thinking drop, content_filter, tool_result image drop, image-capability 400) are likewise absent — an uncovered "config lies quietly" dimension adjacent to but distinct from local-window-knowledge-poisoned.

### claude-code-router (musistudio) v3.0.15

**Conditional rule engine (content-aware routing dimensions)**

Current v3 routing docs: rules match on request.header (case-insensitive, e.g. user-agent) and request.body via dot-path lookup (e.g. messages.0.role, tools) with operators ==, !=, >, >=, <, <=, 'starts with', 'contains', 'contains deep' (recursive), 'not contains'. First enabled matching rule wins (ordered list). Matching rules apply rewrite operations: Set, Delete, Append/Prepend to array, Remove/Replace in array — typically 'request.body.model = provider/model'. Repo at v3.0.15 (released 2026-07-20), 36.1k stars.

Fonte: https://github.com/musistudio/claude-code-router/blob/main/docs/src/content/docs/en/configuration/routing.md

**Failover / retry modes**

Per-rule 'On failure' setting with three modes: Off (single attempt), Retry (same model on 408/409/429/5xx, honors upstream Retry-After, else exponential backoff 1-30s per attempt), Fallback targets (switches through an ordered chain of backup models on any 4xx/5xx). Fallback attempts surfaced in logs via x-ccr-fallback-* headers plus 'route reason', 'resolved provider', 'resolved model' fields.

Fonte: https://github.com/musistudio/claude-code-router/blob/main/docs/src/content/docs/en/configuration/routing.md

**Custom router hooks (Node.js script rules)**

Script rules are JS modules returning {model, rewrites[], fallback:{mode:'model-chain', models[], retryCount}} or null to pass. Content-aware inputs: input.body, input.headers, input.model, input.sessionId, input.apiKeyId, and input.summary.* (text samples, message count, tool names, image presence). Sandbox API: api.fetch(url), api.fs.readText/readJson/writeText/writeJson, api.env(name), api.hash(value) for percentage-rollout bucketing. Limits: 64 KiB file, 32 rewrites/rule, 2000ms default timeout, top-level await allowed, no require/import.

Fonte: https://github.com/musistudio/claude-code-router/blob/main/docs/src/content/docs/en/configuration/routing.md

**Subagent model routing**

Built-in 'Subagent/Workflow auto-routing': CCR injects model descriptions into agent prompts and instructs Claude Code to tag spawned agents with <CCR-SUBAGENT-MODEL>provider/model</CCR-SUBAGENT-MODEL>; CCR extracts the tag from the system prompt or first two user messages and routes that subagent's requests to the tagged model. Also a built-in 'Claude Code' route that detects Claude Code clients (x-anthropic-billing-header) and auto-routes unrecognized models to the profile's Agent Config model, stripping the billing system message.

Fonte: https://github.com/musistudio/claude-code-router/blob/main/docs/src/content/docs/en/configuration/routing.md

**Background/small-fast-model slot per agent profile**

v3 Agent Config profiles carry a 'model' plus a separate 'small fast model' slot for Claude Code (background/haiku-class traffic), with per-agent settings-file management and profile launch via 'ccr <profile> [cli|app]'. The v2-era scenario slots (default/background/think/longContext/webSearch/image) are not present in v3 profile docs — replaced by rules + script routing.

Fonte: https://github.com/musistudio/claude-code-router/blob/main/docs/src/content/docs/en/guides/agent-profile.md
